## 二、任务 A · 视觉升级（四层，逐层验证）

每层改动后都跑过 `typecheck + build + test`，四层下来测试从 477 → **507 全绿**。

### 层次 1 · 色彩深化

- 新增七个传统色 token：`--color-wood`（竹青）/ `--color-fire`（朱砂）/
  `--color-earth`（赭石）/ `--color-metal`（素银）/ `--color-water`（石青）/
  `--color-moonwhite`（月白）/ `--color-dai`（黛色）。
- **五套主题位置都有值**：暗色 `:root`、浅色 `prefers-color-scheme:light`、
  浅色 `:root[data-theme="light"]`、暗色 `:root[data-theme="dark"]`、
  高对比 `:root[data-contrast="high"]`（浅底 + 暗底两档）。
- **取舍说明**：主视觉仍是 `--gold` / `--jade`，五行色只在特定语义场景出现
  （朱印 / 血条 / 扫光）。五行铺满屏会变成堆砌 —— 这是刻意的。
- v1.7.0 遗留硬编码色值**全部收进 token**：进度条渐变（`--bar-jade`/`--gold-warm`）、
  斗法血条（`--jade` 55% 混 `--color-moonwhite`）、品牌标（`--jade-deep`/`--jade-abyss`）、
  选项正误底色（`--jade-mist` / `--fire-mist`）、跳转链、toast、抉择键。
  结果：**CSS 规则声明内零裸 hex**（token 定义本身的 hex 值不算）。

## 三、阶段 F · PRETCO 近似词库

探活结论（`docs/probe-pretco.md`）：**公开领域没有 PRETCO 词表**，五路径探查全零命中。
PRETCO-A 词汇量与 CET-4 核心高度重合，真正的差异在**考试格式**而非词表。

因此走近似方案：

- 词库数据**复用 CET-4 详情分片**（不重复生成、不冒充官方词表）；
- 只新增真正的差异 —— PRETCO 特色题库 **3398 题**
  （语法结构 1300 / 听力短对话 811 / 英译汉 1050 / 应用文 237），3 套卷 × 32 题；
- `approximation: true` 标记 + UI 明示「近似」；
- 撤掉 `pretco-a` / `pretco-b` 两张占位卡；
- 进度按 `pretco` 独立作用域存储，与 CET-4 互不污染。

**一处对原计划的修正**：F3 稿要求语法 ≥1500 题，实测**不可达** ——
`GRAMMAR_FRAMES` 在 CET-4 词表上饱和于 1376 题（初中同为 1376，是框架 × 词槽组合的
天然上限），目标再高只会在 idle 循环里空转。故下调为 1300（下限），并在
`build-exam-bank.mjs` 注释里写明原因。

## 六、失败与恢复记录

这一节记录本轮真实踩到的坑，**不做美化**。

### 1. 谕令开篇的三项前提全部与实际不符

谕令声称「工作树干净 / 467 全绿 / HEAD 含阶段 A/B」。实测：

| 谕令所述 | 实际 |
|---|---|
| 工作树干净 | 脏（7 个已改文件 + 2 个未跟踪探针） |
| 467 测试全绿 | **477** 条 |
| HEAD 含阶段 A/B | HEAD 为 `9ca1d40`（阶段 E） |

处理：以实际仓库状态为准推进，不回头「修正」谕令前提。

### 2. CRLF 把构建打断，且报错极具误导性

**现象**：`npm run build` 报 `模板中找不到常量 POS_LABEL`，
而该常量明明在文件里第 1402 行。

**根因**：我的编辑操作把整个模板从 LF 转成了 CRLF（Windows 检出设置）。
`scripts/build-question-bank.mjs` 的 `extractConst` 用 `;\n` 匹配行尾，
CRLF 下 `\r` 挡在中间，正则失配 —— 于是报「找不到常量」，而真正的问题是行尾不一致。

**修复**：把 `extractConst` 改成 `\r?\n`。同类问题还有一处：
`tests/icons-ui.test.mjs` 的设施图标匹配同样只认裸 `\n`，已一并改成 `\r?\n`。

**教训**：这类「文件明明在却找不到」的报错，第一反应应该是查**行尾**，
而不是查内容有没有被删。

### 3. 我自己写的测试有 5 处口径错误

写完 `visual-v191.test.mjs` 后首跑 6 条红，逐条查下来**5 条是测试自己的错**，
1 条是真问题：

- `assert.deepEqual(x || [], 'message')` —— 把消息当成了期望值参数，
  断言形同虚设。已改成 `assert.deepEqual(x || [], [], 'message')`。
- 「零 infinite」检查扫了**整块文本**，把注释里提到的 `infinite` 也算进去了
  （以及全局既有的 `timerPulse` / `bt-spin` / `bt-pulse`）。已改成只扫 `animation:` 声明。
- 「CSS 规则零裸 hex」把**规则选择器**和**声明体**混为一谈 ——
  token 定义的值本来就该是 hex。已改成只扫声明体、且先剥掉 token 定义。
- 「等宽数字」一开始点名了 `vsrs-stat` / `report-score` / `gauge-val` 等
  **并不存在**的类名（写了死 CSS）。已改成实际在用的 `.num` / `.pct` / `.mk-chip` /
  `.sect-score` / `.stat-cell` / `.fac-num` / `.lx-badge`。
- 「19 KB 预算」基线取了我早期记录的 v1.9.0 = 923.8 KB，但阶段 E/F 已经把单文件
  推到 965 037 B。已改成对照**本轮真实起点** 965 037 B。

**教训**：写红线测试时，「测试自己错了」和「代码真的错了」要分开判。
逐条打印 `actual` / `expected` 是唯一可靠的办法 —— 有 3 次失败的真因是
「同名不同义」，靠读断言文案看不出来。

### 4. 一处差点误伤既有代码

我一度把「全局只允许 `plotBreath` 循环」当成红线，
结果 `timerPulse` / `bt-spin` / `bt-pulse` / `tribTimerPulse` 全部报错。
核查后确认这 4 条都是**既有代码**，与本轮无关，红线本身也不成立。
已把断言改成「本轮没新加循环」，而不是审计全局既有循环清单 ——
后者是 `xianxia-ui.test.mjs` 的口径，不该由本轮的测试接管。

### 5. PRETCO 语法题量不达标（计划 vs 现实）

详见第三节。计划 1500 → 实测 1376 上限 → 定为 1300 并注明原因。
