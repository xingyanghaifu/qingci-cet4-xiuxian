## 4. 未完成清单（按建议顺序）

### P1-9 · `<h1>` 可访问名称 ✅ 已完成

原状：`<h1>` 的可访问名称是 **9 个模块名拼接**。屏幕阅读器不认 `:has()`，
而 9 个 `.mt` span 全部常驻 DOM，只有 CSS 在视觉上藏起 8 个 ——
读屏会把「试炼殿 背单词 单题 口语小径 心魔本 词谱 卷面与洞府 问道斗法 灵田」
连读成一句，而不是当前模块。

**做法**：静态给 9 个 span 写死 `aria-hidden`（默认 `paper` 为 `false`），
再由 `switchTab` 每次切换时重设 —— 全站 23 处切模块都过这个函数，不必逐个补。

**两个必须知道的细节**：

1. **trial 面板要分叉**。`data-tab="trial"` 对应两个标题（`words` / `single`），
   判定口径必须与 `.on` 按钮的消歧完全一致，否则会出现
   「按钮亮着单题、标题读成背单词」。`switchTab` 里已复用同一套条件
   （含模考进行中 `!paper` 的边界）。
2. **降级分支不能只靠 `aria-hidden`**。`@supports not selector(:has(*))` 原本让
   9 个标题**全部可见**、用 `·` 分隔；此时若给 8 个加 `aria-hidden`，
   就成了「屏幕上看得见却读不到」（ARIA 大忌）。故把降级 CSS 改成
   `.mt[aria-hidden="false"]{display:inline}` —— 可见性与可访问名同源，
   一个属性同时管两件事，不可能脱钩。

守卫：`tests/form-a11y.test.mjs` 6 条（静态计数 ×2、运行时 ×4），
其中「交叉验证」一条把 CSS `:has()` 规则独立解析一遍，
与 `switchTab` 的 `aria-hidden` 对答案 —— 两条路径必须收敛到同一模块。

### P2-13 · 首访主题跟随系统 ❌ **不做（审计前提不成立）**

审计原文：「`p === null` 时强制 `dataset.theme='dark'`，与
`<meta name="color-scheme" content="light dark">` **矛盾**」。

**实测这个「矛盾」不存在。** 用真浏览器在系统浅色 + 无存储（首次访问）下探测：

| 探测项 | 实测值 |
|---|---|
| `data-theme` | `dark` |
| `<html>` computed `color-scheme` | **`dark`** |
| `body` 背景 / 前景 | `rgb(13,17,23)` / `rgb(230,237,243)` |
| 原生 `<input>` computed `color-scheme` | **`dark`** |
| 原生控件背景 | `rgb(13,17,23)`（与页面同族，无花屏） |

原因：`:root[data-theme="dark"]{…color-scheme:dark}` 在**运行时覆盖了**
`<meta name="color-scheme">` 的初值。所以原生控件、滚动条都按深色渲染，
**与页面一致**。审计只比对了 meta 标签的静态文本，没看 computed 值。

**另外这也不是「没人管」的默认值**，而是 v1.6 的显式设计（暗色为品牌基线）：
- `src/services/theme.ts:37-38` 有明确注释「行为变更（v1.6）：无存储 → 暗色默认」
- `tests/theme-shortcuts.test.mjs:65` 与 `tests/a11y.test.mjs:142` **两条测试专门锁着它**
- `readPreference(null)`（存储不可用）仍返回 `auto` 跟随系统 —— 降级路径是通的

**结论**：这是**产品口味**（首访用哪个主题），不是缺陷。
「跟随系统」这个能力本身已经完整（设置里有 `auto` 档，且已通过测试）。
要改默认值 = 改产品定位，需要用户点头；与 P0-2 同类，不单方面改。

### 4.8.1 构建期 CSS 压缩（`6a5225c`）—— 一次性回收 20.9 KB

**动机**：`build.mjs` 的 4c 一直只压 `<script>`，`<style>` 段原样进产物 ——
其中约 18 KB 是中文设计注释，运行时零价值却实打实占预算。
产物 925 618 B 时，19 KB 预算只剩 **5.04 KB**，任何新玩法都塞不进。

**做法（4d，紧接 4c）**：

| 要点 | 说明 |
|---|---|
| 去块注释 + 收缩结构性空白 | 只动 `{ } ; : , >` 周围与连续空白 |
| **引号感知** | 单/双引号内原样保留 —— 保护 `url("data:image/svg+xml,…")` 宣纸纹理里的语义空白 |
| **不用 esbuild 转 CSS** | 它会把 `@media`/`@supports` 重新排版，而多条守卫按**源码书写形态**断言（`@media (prefers-reduced-motion:reduce){`、`html:root[data-contrast="high"]{`），重排会大面积假失败 |
| 尊重 `SKIP_MINIFY=1` | 沿用既有诊断开关，用于「问题是不是压缩引入的」对照实验 |

**收益**：97.4 → 76.5 KB（省 20.9 KB）；产物 925 618 → 904 237 B；
剩余预算 **5.04 → 25.92 KB**；距硬顶 950 000 还有 44.69 KB。
源码注释原样保留（166 处，可读性不受影响）。

**守卫**：`tests/css-minify.test.mjs`（7 条）。不只断言「压缩生效」，
更断言**没压坏语义**：注释已剥离、源码注释保留、大括号平衡、data URI 完整、
6 条关键规则原样在、体积收益未被回退。

### 4.8.2 奇遇效果补全（`6241803`）—— 修掉 5/6 个「空头支票」

**这是本轮最有价值的发现**。`encounters.ts` 定义了 6 个奇遇、每个都带 `effect` 标识，
但模板的 `applyEncounter` **只对 `qi_rain` 做了真实结算**，其余 5 个只弹一句 toast：

```
scroll     → '拾得残卷 · 待与词库联动（book 解锁）'   ← 从未联动
beast      → '灵兽来投 · XXX 认主了'                ← 认主了但没有灵兽
cave       → '效果已生效（1 小时内）'                ← 没有任何效果
old_master → '效果已生效（1 小时内）'                ← 同上
demon_raid → '去心魔录迎战'                          ← 只是指路
```

**判据**：实测 6 个 effect 字符串**全仓库各只出现 1 次**（仅在自己的定义里），
即**没有任何消费点**。这是最亏的一类缺陷：有内容、有期待、无回报。

**旧测试为何抓不到**：它只断言「事件池字段完整」（`assert.ok(e.effect && …)`）——
只检查 `effect` 这个**字符串存在**，从不检查它**被消费**。
又一个「字符串里有 ≠ 真的发生」（同坑 0）。

**新增 `src/services/encounter-effects.ts`**（纯函数 + 独立存储键）：

| 奇遇 | 真实效果 | 关键约束 |
|---|---|---|
| `qi_rain` | 30–80 灵石 | 区间随机源可注入，测试可复现 |
| `cave` | 洞天福地：1 小时修为 **×1.5** | 重复触发是**续期**（叠在剩余之上），非覆盖 |
| `old_master` | 老道指点：今日重点词，答对它 **+10 修为** | **跨日自动失效**（否则昨天的重点词一直生效） |
| `scroll` | 拾得残卷：产出待解锁词 → 走 `economy.grantItem` 真解锁深度解析 | 与商店购买同一条链路 |
| `beast` | 灵兽来投：真认主 + 永久修为 **×1.1** | **只认一只**，重复触发不换主 |
| `demon_raid` | 心魔来袭：真的切到心魔本并触发复习入口 | 不再只是指路 |

**设计**（与 `gamification.ts` 同一套路）：
- 纯状态转移 `applyEffect(type, state, ctx) → { state, outcome }`，

- 三条红线：增益纯加法（不扣既有资产）、倍率有上限（1.5×1.1，不随做题量增长）、

`settle()` 的修为收益过 `encQiBonus()`（倍率 + 重点词加分）；

### ⚠️ 真浏览器验收抓到的两个缺陷（单测抓不到，务必记住）

**1. 签名不匹配 —— 只读判定必须支持「省略 state 即读存储」**

只读判定（`qiMultiplier` / `activeBoostLabels` / `focusBonusFor`）最初把 `state`
设成**必填**，而模板按**无参**调用（`qiMultiplier()`）。结果模板传 `undefined`
→ 一律判定「无增益」→ **倍率恒为 1、增益徽标永不显示**。

**为什么单测抓不到**：单测总是显式传 `state`，永远走不到这条路径。
**只有真浏览器（走模板真实调用形态）才暴露**。

修法：`state` 省略（`undefined`）时自动读存储；显式传 `null` 则表示
「确实没有状态」，不读存储。已补 5 条守卫把该契约 + 模板调用形态钉死。

**2. 词表上下文缺失**：`old_master` / `scroll` 需要词表，服务层直调时拿不到 →
需从页面 `WORDS` 取（已确认可达，4540 词）。

> 教训：**服务层的签名必须与模板的真实调用形态一起验**。
> 静态单测覆盖不到「调用方怎么调」，这需要真浏览器端到端。

### 4.8.3 未领取奇遇不再丢失（`bf29e80`）—— 同类缺陷的第二次出现

**判据与 §4.8.2 完全同法**：`encounters.listPending()` 已实现、已导出
（`QingciServices.encounters.listPending`）、已有单测覆盖，
但**模板从未调用它**（全模板 grep 0 次）。

**后果**：奇遇掷出后若用户没点「领取」就刷新/关页，那条奇遇**永久丢失**
（库里留着 `resolved:false` 的记录，再也没有任何代码读它）。

**修法**：新增 `restorePendingEncounters()`，开机读 `listPending()`
（未结算且未过期）取最近一条重新弹出通知条。
「只恢复一条」是有意的 —— 通知条是单例（`noticeEl`），多条会互相顶掉；

### 4.9.3 后续修正：折扣不再临时改共享常量（`5083d09`）

`1e053be` 让藏经阁折扣生效时用的办法是**临时改写 `ITEM_CATALOG` 里的对象**：

```js
item.price = payPrice;  // 共享常量被改写
ES.purchase(...)
restore();
```

真浏览器验收时暴露两个问题：
1. **按钮状态错乱**：`renderExtras` 用 `spirit < item.price` 判灰显，
   而 `item.price` 被临时改写/还原，UI 与实付价可能不一致；
2. **本质脆弱**：`ITEM_CATALOG` 是模块级共享常量，临时改写会在渲染 /
   并发购买时被别的调用点读到 —— 静默串味，正是本仓库反复踩的坑型。

**改法**：`economy.purchase` 新增加性可选参数 `options.priceOverride`：

| 要点 | 说明 |
|---|---|
| 不传时 | 行为与既有**完全一致**（有测试钉死） |
| 取值校验 | 只接受「有限正数且**不高于目录价**」→ 防加价、防 NaN |
| 退款 | 按**实付价**退（原来退 `item.price`，会与实付产生净额偏差） |

模板侧：`doPurchase` 传 `priceOverride`；`renderExtras` 用折扣价判灰显
（否则建成藏经阁后按钮仍按原价灰显，折扣形同虚设）。

**真浏览器真实购买路径验收**：未建成扣 50；建成藏经阁扣 40，
toast「参悟古籍生效 · ability（藏经阁优惠 -10 灵石）」。

> **教训**：给「共享常量」打补丁（临时改写再还原）比改接口签名更危险 ——
> 因为它把状态泄漏到了所有并发/异步读取点，而且**测试很难覆盖**。
> 宁可加一个显式的、带校验的可选参数。

**另新增**（`3b27b0c`）`scripts/fetch-audio-from-prod.mjs`：
从线上回捞听力音频的灾难恢复脚本。背景是 TTS 主后端被微软 Sec-MS-GEC
校验拒绝（403），而线上已托管完整音频（7915 条 / 332 MB）。
内置安全闸：取回前逐条比对 `textHash`，不一致即中止 ——
防止把过期音频写进 `dist/` 导致「听力念错内容」（极难察觉）。
**注意**：Node 的 `fetch` 默认不读 `HTTP_PROXY`，必须加 `--use-env-proxy`，
否则退化为 ~2 KB/s 且大量失败（实测踩过）。

## 4.11 内联词库改紧凑列式（第四轮）—— 一次性回收 101.9 KB

### 问题：预算见底

第三轮结束时单文件 924 591 B，19 KB 增量预算**只剩 6.04 KB** —— 任何新玩法都塞不进。

### 定位：102 KB 是纯键名开销

内联的 CET-4 词库（4540 词）原本是**对象数组**：

```json
[{"w":"a","ipa":"","zh":"art.一(个)；每一(个)","short":"一"}, …]
```

每条重复四个键名（`"w":` / `"ipa":` / `"zh":` / `"short":`）约 23 字节，
4540 条 = **约 102 KB 的纯键名开销**（零信息量）。

> 先确认过：JSON 本身**已是**紧凑序列化（无多余空白），
> 所以只能从**结构**上省 —— 这也是为什么「压空白」那条路收益为 0。

### 做法：列式编码 + 统一解码器

内联词库改为列式：`{"k":["w","ipa","zh","short"],"v":[["a","",…],…]}`

| 项 | 值 |
|---|---|
| 词库字节 | 373.0 KB → **271.0 KB**（省 101.9 KB） |
| 产物 | 924 591 → **825 203 B** |
| 剩余预算 | 6.04 KB → **103.10 KB** |
| 相对基线 | 首次**低于基线 84.10 KB** |

新增 `core/utils.js` 的编解码（CommonJS，浏览器 / Node / Worker 三处共用）：

| 函数 | 说明 |
|---|---|
| `encodeLexicon()` | 词条数组 → 列式 |
| `decodeLexicon()` | **兼容两种格式**：对象数组原样返回、列式还原；非法输入返回 `[]`，绝不抛错 |
| `lexiconFromHtml()` | 从 HTML 文本取出并解码 |

新增 `src/core/utils.d.ts`：core/utils.js 是 CommonJS，tsconfig 开了 strict，
TS 侧 import 会报 TS7016。补一份**最小手写声明**（只列 TS 侧用到的成员）。

### 覆盖所有消费方（8 处，全部改走 decodeLexicon）

| 位置 | 读的是 | 说明 |
|---|---|---|
| 模板 5 处解析点 | 产物（列式） | 主词源 / 两个子脚本 / 深度解析 / 词谱 |
| `src/entry/services.ts` | — | 把 `decodeLexicon` **挂到全局**（模板才能用） |

## 4.12 灵根（五行天赋）—— 第三期玩法

### 为什么做这个

修仙叙事里「灵根」是**身份认同**的核心：五行灵根决定你擅长什么、走什么路。
本项目此前**完全没有这个概念**（全仓库 grep「灵根」0 次）。

而它天然能挂到**已有的真实数据**上：`state.memStats` 已按六种题型记录
「答对 r / 总数 n」。于是灵根不是随机抽的，而是**从实际表现里长出来的** ——
既满足叙事，又让用户看清自己的强弱项（**游戏化服务于学习**，而非另起一套）。

### 五系 ← 六题型（映射有语义，不是硬凑）

| 系 | 题型 | 叙事解释 |
|---|---|---|
| 金 | `spell` 拼写默写 | 锋芒精确，一字不差 |
| 木 | `zh2en` 中译英 | 生长输出，主动生成 |
| 水 | `listen` 听音辨词 | 声流入耳，感知 |
| 火 | `pos` 词性判断 | 洞察属性，快速辨析 |
| 土 | `en2zh` + `similar` | 承载与分辨（理解 + 形近辨析） |

### 机制（`src/services/spiritual-root.ts`，纯函数）

| 项 | 规则 |
|---|---|
| **样本门槛** | 某系作答 < **5 题**视为「未显」，不参与判定 —— 防「做 1 题全对 → 天灵根」 |
| **纯度** | 主导系作答 / 已显系总作答 |
| **档位** | 单系已显或纯度 ≥70% → 天灵根；≥45% → 双灵根；≥30% → 三灵根；否则杂灵根 |

- **不制造焦虑**：灵根是「倾向描述」不是评分；样本不足明说未显；
  杂灵根是特色不是缺陷（有测试专门断言文案不含「差/弱/失败」）
- **不鼓励刷题**：由**正确率**决定，不是题量 ——
  有测试断言「十倍题量、同正确率 → 纯度不变」
- **不侵入学习**：纯只读推导（读 `memStats`），不改 SRS、不写存档、不影响出题

### 模板接线

学情看板新增灵根卡：五系各自正确率（各用**五行 token** 上色，未显降为中性色）、

## 5. 四个必须知道的坑（都会造成静默错误）
### 坑 0：属性写在标签名之前 → 控件「不存在」，而字符串测试看不出来

**2026-10-07 发现的真实缺陷，影响 12 个控件 / 43 处调用点。**

之前 P1-8「控件可访问名」用脚本批量插入 `aria-label`，把属性插到了**标签名之前**：

```html
<aria-label="搜索单词或中文释义" input id="q" placeholder="搜单词或中文">
<!-- ↑ 第一个 token 必须是标签名，这里却是属性 -->
```

浏览器的容错解析把它当成**自定义元素** `<aria-label>`，于是真正的
`<input id="q">` **根本不存在**：

- `$('q')` 返回 null → `renderCodex()` 抛 TypeError → **词谱页整页打不开**
- 12 个控件（输入框/下拉/文本域）全部失效，涉及 43 处调用点

**为什么测试全绿还漏掉了**：P1-8 的测试扫的是**源码字符串**
（`tag.includes('aria-label="X"')`），而字符串确实包含 ——
只有**浏览器解析后**才看得出标签不存在。

**防线**：`tests/markup-structure.test.mjs`（4 条）用**宽松 HTML 解析**判断标签
是否真的存在，而不是字符串匹配。另有运行时验收
`npm run verify:minified:runtime` 断言 12 个控件在真实 DOM 里都在。

> 教训：**「字符串里有」≠「浏览器认」**。凡是关于 DOM 结构的断言，
> 必须用解析/运行时验证，不能用 `includes`。

### 坑 1：Cloudflare Pages 的 SPA 回退会伪装成「文件存在」

任何未知路径都返回 **200 + 首页 HTML**。所以 `.json()` 抛的是**解析错误**，不是 404 —— 掩盖了「文件根本不存在」这个事实。

本项目因此踩了两次：PRETCO 词表（`wordListPath === ""`，词表复用 CET-4）、以及 `/robots.txt` 返回 981 KB HTML。

**排查线上问题前先确认路径真实存在**，别被 200 骗了。

### 坑 2：CRLF ↔ LF 会悄悄顶破体积预算

模板 `src/index.template.html` 是 **CRLF**（5,772 行）。用编辑工具整文件改写时可能变成 LF，**每行少 1 字节**，5617 行就是 −12 KB，直接把单文件预算顶破。

**已在本轮踩过一次**：文件一度从 811 KB 掉到 475 KB。

**做法**：改模板优先用 Node 脚本按字节写回（`writeFileSync`），改完用脚本校验 `LF 数 === CRLF 数`。**不要**用 `WriteAllText` + `-replace` 的组合操作整份模板。

### 坑 3：体积预算的三次重定基（**当前基线 911,318 B**）

| 时点 | 基线 | 说明 |
|---|---|---|
| 原始 | 965,037 B | 阶段 F / PRETCO 之后，上限 19 KB |
| 2026-10-07 第一次 | 984,120 B | 实测开工前 HEAD 已用掉 18.64/19 KB，只剩 369 B |
| **2026-10-07 第二次（当前）** | **911,318 B** | **构建期剥离内联脚本注释后重定基** |

**为什么第二次重定基**：要做「游戏性 + 修仙机制」改造，而旧基线只剩 **4.73 KB**。
于是在 `scripts/build.mjs` 里加了内联脚本压缩（去注释 + 压空白 + 语法简化，
**不开 `minifyIdentifiers`** —— 这些脚本跨块共享全局名，改短名字会静默断开引用）。
实测省 **85.4 KB**，产物 998,731 → **911,318 B**。

**这次重定基与第一次不同**：第一次是「预算被吃完了，只好承认现实」；
这次是**真的把体积降下来了**，释放的空间可以用于新功能。

**两条守卫**（`tests/visual-v191.test.mjs`）：
1. 体积在新基线 + 19 KB 内，**且产物必须 < 950,000 B**
   （防止压缩收益被新代码悄悄吃完）
2. 产物内联脚本**不得有块注释**（防压缩被回退）；同时断言**源码注释仍在**
   （剥离只发生在产物，源文件要保持可读）

**诊断开关**：`SKIP_MINIFY=1 npm run build` 可跳过压缩，
用于「某个问题是不是压缩引入的」对照实验。

## 7. 我的错误模式（这几个坑我反复踩）

1. **`assert.deepEqual(实际值, '说明文字')`** —— 把说明写进了「期望值」槽位，断言变成永真。本轮因此出现「3 个测试假绿」。

2. **验收脚本本身出错，却当成产品 bug 去改**。本轮 5 次「失败」全部是我的脚本口径错（404.html 以 `<!DOCTYPE` 开头是对的、对话框是 11 个不是 12 个、`sitemap.xml` 本就不该出现在 HTML 里）。
   **教训：先证伪「我的判据错了」，再动产品。**

3. **假 DOM 写错却怪代码**。造 `classList` 用 `indexOf` 拼串、在 `new Function` 参数里写带点的名字、把 toggle 语义搞反 —— 都会让测试假失败。

4. **临时脚本忘删**（`_audit.mjs` 曾误入版本库，已 `git rm --cached`）。临时文件名统一 `_` 前缀，收尾用 `Remove-Item`。

5. **PowerShell 环境限制**：没有 `&&`（用 `;`）；没有 `head`/`tail`/`grep`/`gzip`；用 `npm.cmd` 不是 `npm`；用 `Select-Object -Last N`、`Select-String`。
   `node -e` 里带正则方括号或点号参数名会被 mangle —— **改写成临时 `_*.mjs` 文件**再跑。
