# 部署说明

本文档说明「青词天路」的三种部署方式，以及线上环境的实测数据与已知限制。

---

## 一、部署方式总览

| 方式 | 适用场景 | 是否需要账号 | 公网可访问 | 稳定性 |
|---|---|---|---|---|
| 本地直接打开 | 个人自用、离线 | 否 | 否 | — |
| 本地 HTTP 服务 | 局域网分享、健康检查 | 否 | 否 | 高 |
| Cloudflare 隧道 | 临时演示、公网验证 | **否** | **是** | 中（回源本机） |
| 静态托管 | 生产环境、长期使用 | 是 | 是 | 高 |

---

## 二、本地 HTTP 服务

### 启动

```bash
npm install     # 零外部依赖
npm run build   # 构建产物到 dist/
npm start       # 默认 http://127.0.0.1:4173
```

### 可用接口

| 端点 | 方法 | 说明 | 返回 |
|---|---|---|---|
| `/healthz` | GET | 健康检查 | 200 + JSON（含词库条数、版本、运行时长） |
| `/api/meta` | GET | 应用元信息 | 200 + JSON（题型、特性清单） |
| `/` | GET | 应用页面 | 200 + HTML |

### 健康检查示例

```bash
curl -s http://127.0.0.1:4173/healthz
```

实测输出：

```json
{
  "status": "ok",
  "version": "1.0.1",
  "uptimeSeconds": 12,
  "checks": {
    "lexicon": { "ok": true, "count": 4540, "expected": 4540 },
    "build": { "ok": true, "artifact": "dist/cet4-xiuxian.html" }
  },
  "runtime": { "node": "v24.18.0", "platform": "win32" },
  "timestamp": "2026-09-30T03:34:17.934Z"
}
```

### 自定义端口与监听地址

```bash
PORT=8080 npm start           # 换端口
HOST=0.0.0.0 npm start        # 监听所有网卡（局域网可访问）
```

## 三、Cloudflare 快速隧道（公网访问，免账号）

适合临时演示：把本地 4173 端口映射到公网 HTTPS 地址。

```bash
# 1) 先启动本地服务
npm start

# 2) 另开一个终端，建立隧道
npx cloudflared tunnel --url http://127.0.0.1:4173
```

启动成功后会打印公网地址，形如：

```text
Your quick Tunnel has been created! Visit it at:
https://<随机名>.trycloudflare.com
```

### 实测结果

| 项 | 实测值 |
|---|---|
| 健康检查状态码 | 200 |
| 健康检查响应时间 | 稳定态 422–874ms（阈值 2000ms） |
| 应用页面 | 200，约 1.0s |
| API 元信息 | 200 |

### 已知限制（重要）

1. **回源到本机**：隧道只是转发，本机服务停止则公网地址失效。
2. **免账号隧道无可用性保证**：Cloudflare 官方明确说明此类隧道不保证 uptime。
3. **冷启动抖动**：长时间无访问后首次请求可能达 2s 左右，属隧道建连开销，非接口性能问题。
4. **地址不固定**：每次启动会分配新的随机子域名。

**结论**：适合演示与验收，不适合作为生产环境。

## 四、静态托管（推荐用于生产）

应用是**单文件静态资源**，不依赖服务端渲染，可直接托管。

### 构建

```bash
npm run build
# 产物：dist/cet4-xiuxian.html（约 464 KB，零外部依赖）
```

### 各平台部署

| 平台 | 命令 | 备注 |
|---|---|---|
| Cloudflare Pages | `npx wrangler pages deploy dist` | 需 `wrangler login` |
| Netlify | `npx netlify deploy --dir=dist --prod` | 需 `netlify login` |
| Vercel | `npx vercel --prod dist` | 需 `vercel login` |
| GitHub Pages | 推送后 Settings → Pages 选分支 | 需仓库写权限 |

> 注意：静态托管不执行 Node，因此 `/healthz`、`/api/meta` 两个**动态接口不可用**。
> 静态平台自身提供可用性监控；若需保留健康检查接口，请使用带服务端的环境
> （如 Render、Railway、云服务器 + `npm start`）。

---

## 五、服务端部署（保留健康检查接口）

若需在生产保留 `/healthz`，部署 `server.mjs` 即可。该文件仅依赖 Node 内置模块。

```bash
# 服务器上
git clone <repo> && cd qingci-cet4-xiuxian
npm run build
PORT=8080 HOST=0.0.0.0 npm start
```

### 性能优化（已内置）

| 优化 | 说明 | 效果 |
|---|---|---|
| gzip 压缩 | 对 >1KB 的文本响应自动压缩 | 464 KB → 142 KB（31%） |
| 压缩缓存 | 压缩结果进程内缓存并预热 | 消除重复压缩开销 |
| 启动预热 | 服务启动时预先压缩页面 | 降低首次请求延迟 |

## 六、验收命令

```bash
npm run verify      # 一键：构建 + 测试 + 文档核验 + 健康检查
npm run healthcheck # 单独校验健康检查状态码与响应时间
```

`healthcheck.mjs` 会校验状态码为 200 且响应时间低于阈值（默认 2000ms），
不满足则以非零码退出，可直接接入 CI。

## 七、常见问题

**Q：公网地址打不开？**
A：检查本机服务是否仍在运行（`npm start`）；隧道与本机服务是两个进程，任一停止都会导致不可访问。

**Q：健康检查偶发超过 2 秒？**
A：免账号隧道长时间空闲后会断开连接，首次请求需重新建连。预热一次后即恢复正常水平。

**Q：能否长期用隧道地址？**
A：不建议。请改用静态托管或带服务端的环境。

**Q：静态托管后进度会丢吗？**
A：进度存在浏览器 localStorage，与部署方式无关。但清理浏览器缓存会丢失，建议定期导出 JSON。
